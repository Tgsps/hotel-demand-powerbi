# Plan: Hotel Booking Demand, Power BI portfolio project (PL-300 coverage)

Status: planning only. Nothing has been built. Source IDs (Sxx) refer to docs/LEARN-SOURCES.md. Risks (Rxx) refer to docs/RISKS-AND-OPEN-QUESTIONS.md.

## Goal

A Power BI Desktop project (PBIP, kept in git) built on the Hotel Booking Demand dataset. It shows the PL-300 skills a junior data analyst is expected to have:
- data preparation in Power Query,
- a star-schema model,
- DAX measures,
- a multi-page report,
- row-level security.

Skills that need the Power BI Service are covered only if the owner gets Service access (R02). Otherwise they are documented as runbooks and marked as such in the coverage table.

## Roles

- **CC (Claude Code)** writes text only:
  - Power Query M,
  - DAX scripts,
  - TMDL edits once a project exists,
  - theme JSON,
  - docs,
  - check scripts.
  CC does not run Power BI and cannot see visuals.
- **Owner** does everything inside Power BI Desktop or the Service. That includes downloading the data and confirming the licence. The owner also records the observed numbers back into the docs.

## Assumptions

1. The owner has about 6-8 hours a week. The week estimates depend on this (R11).
2. Desktop is a recent build. Check it in Phase 0 (R05).
3. The owner has Power BI (free) under Microsoft Fabric (Free), with no Pro or PPU (R02). The target is Desktop + My workspace. P0-09 tests what that allows. Phase 4b is limited to what P0-09 confirms.
4. Data files are never committed until the licence is verified, and probably not even then (R01, R03).

## Role-playing dates: the reasoning

Three date roles exist: arrival, booking (arrival minus lead time) and status (check-out or cancellation date).

- **Arrival**: the main business date. Active relationship to the marked 'Date' table, so all time intelligence works on arrival.
- **Booking**: the report needs a matrix of arrival month by booking month (booking window analysis). That needs two date roles filtering at the same time. A single date table with an inactive relationship cannot do this [verified: S21, S22]. So booking date gets its own table.
- **Status**: used for one question only, "cancellations by the date they were cancelled". No visual needs it together with another role at the same time. An inactive relationship plus USERELATIONSHIP in a measure is enough [verified: S22 recommends inactive relationships for this case], and it shows the second pattern for the exam.
- **Fallback**: if P4-03 shows USERELATIONSHIP fails with RLS enabled, replace R3 with a third table 'Status Date' (calculated clone) and an active relationship. The measure M19 then becomes a plain measure.

| Three separate date tables | Works, but then USERELATIONSHIP is not shown at all. Kept as the fallback. |

CALENDARAUTO scans every date column in the model, which gives less control over the range [verified: S18 describes it as covering all model dates]. |
| Auto date/time | It cannot let one date table filter several tables [verified: S18]. Turned off for the file (P2-02). |
| Calendar-based time intelligence | Preview feature [verified: S32]. The portfolio should use GA features. Revisit if it becomes GA. |
| Junk dimension for meal / deposit / customer type / repeated guest | A valid pattern [verified: S21]. Rejected so that each attribute is easy to find in the field list. With small dimensions at this size the cost is negligible [inferred]. |
| Agent and Company dimensions | The IDs have no attributes in the file [not verified: the paper's description of the IDs was not reported]. ## Principles

1. **No row is deleted by default.** The dataset has no booking ID, so identical rows may be different bookings [inferred]. Every rule below either converts a value or adds a flag. The fact table must still have 119,390 rows at the end.
2. **Keep the raw value next to the cleaned value** when a rule changes a number that feeds a measure (adr), so the change can be audited.
3. **Convert types with an explicit culture ("en-US").** The CSV uses "." as the decimal separator [not verified]. Desktop uses the OS regional format by default, and a mismatch produces error values [verified: S15]. Table.TransformColumnTypes accepts a culture argument [verified: S10].
4. **Replace text placeholders before converting types.** If "NULL" is still there when the column is converted to a number, the conversion is expected to give errors [inferred from S15].

## Known issues (from the brief)

### DQ-01 "NULL" text in agent

- Observed: 16,340 rows hold the text "NULL" [verified: planner brief].
- Meaning: "NULL" means "not applicable", not missing [verified: planner, source paper].
- Rule (Power Query):
  ```
  ReplacedAgent = Table.ReplaceValue(Promoted, "NULL", null, Replacer.ReplaceValue, {"agent"})
  ```
  `Replacer.ReplaceValue` matches whole values only, so an agent ID that merely contains "NULL" is not touched [verified: S09].
  Then convert to `Int64.Type` with culture "en-US". The null is kept so the column can be typed. Add `HasAgent = [agent] <> null` (logical). Add a text label column for display: `AgentLabel = if [agent] = null then "Not applicable" else Text.From([agent])`.
- Effect to verify: row count unchanged (119,390). Null count in agent = 16,340. Conversion errors in agent = 0. HasAgent false = 16,340. AgentLabel "Not applicable" = 16,340.

### DQ-02 "NULL" text in company

- Observed: 112,593 rows hold "NULL" [verified: planner brief].

- Effect to verify: rows unchanged. Null count = 112,593. Errors = 0. CompanyLabel "Not applicable" = 112,593.

### DQ-03 Empty country

- Observed: 488 rows with an empty country [verified: planner brief].

  CountryFixed = Table.ReplaceValue(Prev, each [country], each if [country] = null or [country] = "" or [country] = "NULL" then "UNK" else [country], Replacer.ReplaceValue, {"country"})

  A simpler form is two Table.ReplaceValue steps ("" -> "UNK", then "NULL" -> "UNK"). The Country dimension gets one row `UNK` with the label "Unknown".

## Conventions

- Ratios use DIVIDE with no alternate result. A zero or BLANK denominator then returns BLANK [verified: S30, S31], and visuals hide empty groups [verified: S31].
- Boolean filters inside CALCULATE reference columns of one table only, and never a measure [verified: S25].
- "Realized" means not cancelled (IsCanceled = 0). IsCanceled = 1 also covers no-shows: confirmed, see DATA-QUALITY V-01.
- Revenue is an **estimate**: AdrClean x TotalNights for bookings that were not cancelled. The definition of adr in the source paper must be checked [not verified].
- Partial years: arrivals cover 2015-2017 [verified: planner brief], and the first and last years are partial: 2015 is July to December and 2017 is January to August [verified: data profile 2026-11-16, planner; see DATA-QUALITY V-06]. Year-level comparisons across partial years are misleading. Show YoY at month level and let PY return BLANK where the prior month has no data.
